# ML: аналитика текстов отзывов (план, вне MVP)

Сейчас здесь только план. В воркере есть пустая задача `analyze_review_stub`
(`backend/app/workers/tasks.py`) — точка, куда подключится анализ.

## Ограничения

- Тексты отзывов могут содержать ПД (имена, телефоны в тексте). **Никаких зарубежных API**
  (OpenAI, Google и т. п.): модель работает на нашем сервере в РФ или у российского провайдера.
- В логах — только ID отзыва и коды результатов, без текстов.
- Анализ не должен тормозить приём отзыва: только в воркере, после сохранения.

## Что хотим получить

1. **Аспекты и тональность.** Для каждого отзыва — о чём он (мастер, запись, цена, чистота,
   атмосфера…) и с каким знаком. Список аспектов берётся из `code` категорий ниши
   (`backend/app/niches/*.yaml`), чтобы аналитика совпадала с тем, что клиент отмечает сам.
2. **Тренды.** Рост доли негатива по аспекту, филиалу или мастеру за неделю/месяц
   (например, «жалобы на запись выросли в 2 раза»). Считается SQL поверх результатов анализа.
3. **Дайджест.** Еженедельная сводка владельцу и (в бэклоге) мастеру в Telegram через
   `NotificationChannel`: главное за неделю, 2–3 характерные цитаты без ПД.

## Данные

- Источник — `reviews.text` + отмеченные категории как слабая разметка.
- Перед обучением и разметкой — удаление ПД (телефоны, имена) из текстов.
- Тексты клиентов, отозвавших согласие, в датасет не берём. Датасет хранится в РФ.
- Ручная разметка ~1–2 тыс. отзывов для проверки качества.

## Сервис инференса

- Отдельный контейнер `ml` (FastAPI) с небольшой русскоязычной моделью
  (например, классификатор на базе ruBERT), без GPU для MVP-нагрузки.
- Воркер вызывает его из `analyze_review_stub` → результаты в новую таблицу
  `review_analysis` (с `organization_id` и составными FK, как все бизнес-таблицы).
- Модель версионируется, у каждого результата есть `model_version` — можно переразметить.
